## 1. 프로젝트의 한 문장 정의

AI가 코드 작성의 대부분을 수행하는 조직에서 사람이 목적을 정하고, 일을 위임하고, 결과를 검증하고, 운영 책임을 지는 방법을 설명하는 한국어 조직 운영 실무서를 집필합니다.

독자는 읽고 나서 자기 조직의 **운영 원칙, 위임 범위, 완료 기준, 성과 지표, 개선 실험**을 직접 작성할 수 있어야 합니다.

## 3. 해결하려는 독자 문제

다음은 집필 과정에서 인터뷰와 사례로 확인할 문제 가설입니다. 이미 입증된 업계 전체의 현상으로 단정하지 않습니다.

1. 개인은 빠르게 코드를 만들지만 팀은 요구사항 정렬과 리뷰에서 대기합니다.
2. 에이전트에 작업을 맡길 때 권한, 종료 조건, 실패 보고 방식이 불명확합니다.
3. 코드와 테스트를 같은 맥락에서 생성해 잘못된 가정을 함께 통과시킬 수 있습니다.
4. 결과를 만든 과정과 판단 근거가 대화창에 남아 인수인계가 어렵습니다.
5. 코드량·커밋 수·AI 사용률을 성과로 오해할 수 있습니다.
6. 자동화가 확대되어도 장애 대응과 최종 결정의 담당자가 정해지지 않을 수 있습니다.

책의 중심 질문은 **“코드를 빠르게 만들 수 있을 때, 조직은 무엇을 정하고 확인해야 하는가?”**입니다.

## 5. 용어와 집필 가설

### 5.1 이 책의 작업 정의

- **AI 네이티브 조직:** AI 사용을 일상적인 전제로 삼아 업무 흐름·역할·권한·지식·성과 측정을 설계하는 조직입니다. 사용 도구나 사용률만으로 정의하지 않습니다.
- **풀 바이브 코딩:** 이 프로젝트에서는 자연어로 의도를 전달하고 AI가 구현 대부분을 수행하는 개발 방식을 뜻합니다. 사람이 코드·설계·테스트를 확인하거나 직접 수정하는 경우도 포함합니다. 검토 없이 생성 결과를 수용하는 용례와 혼동하지 않도록 서문에서 범위를 설명합니다. 이는 본서의 작업 정의이며 보편적으로 합의된 정의라는 주장을 하지 않습니다.
- **에이전트:** 부여된 도구와 권한 안에서 여러 단계의 작업을 수행하는 AI 실행 주체입니다. 사람과 동일한 책임 주체로 취급하지 않습니다.
- **운영 원칙:** 반복되는 의사결정에서 선택의 근거가 되는 문장입니다. 적용 조건·예외·확인 방법이 따라야 합니다.

용어 정의는 집필 초기에 원출처와 독자 이해를 확인해 확정합니다. 특히 ‘풀’은 코드 생성 비율의 목표치나 무검토 운영을 의미하지 않습니다.

## 6. 범위와 산출물

### 6.1 필수 범위

의도와 요구사항, 작업 위임, 사람과 에이전트의 협업, 아키텍처 경계, 검증, 배포와 복구, 정보·권한 관리, 리더십, 성장과 채용, 경제성, 측정, 지식 관리, 단계적 전환을 다룹니다.

신규 서비스와 기존 시스템을 모두 다루되, 실험용 코드와 고객 운영 코드의 완료 기준을 구분합니다. 규제·민감 환경에서는 검토가 필요한 의사결정 지점을 설명하며, 특정 규정 충족을 보장하는 지침을 목표로 하지 않습니다.

### 6.2 이번 판에서 제외할 범위

- 특정 도구의 화면·명령어를 중심으로 한 사용 설명서
- 프롬프트 모음만으로 구성한 책, 코딩 기초 교육, 모델 학습·추론 인프라 해설
- 모든 조직의 무인화나 특정 생산성 배수의 보장
- 참고 도서의 번역·축약·공식 후속작
- 저장소 생성·공개, 출판 계약, 웹사이트 구축·배포의 실행

## 9. 장별 편집 요구사항

모든 본문 장은 다음 요소를 포함합니다. 소제목을 기계적으로 반복할 필요는 없지만 검토표에서는 확인 가능해야 합니다.

1. 독자가 겪을 수 있는 구체적인 상황과 결정할 질문
2. 핵심 원칙과 적용 조건
3. 원리가 작동할 것으로 보는 이유와 근거 수준
4. 사람·에이전트·조직이 각각 수행할 행동
5. 사례 또는 명시적으로 표시한 가상 시나리오
6. 실패 양상, 반례, 적용하지 않을 조건
7. 바로 수행할 수 있는 행동 3~5개
8. 산출물 예시, 확인 질문, 다음 장과의 연결

설명은 리더가 팀과 대화할 수 있는 수준으로 씁니다. 코드·프롬프트·도구 설정은 원칙을 이해하는 데 꼭 필요한 부분에만 사용하며 변경이 잦은 예시는 부록으로 분리합니다.

### 샘플 장 검증

3장은 ‘요구사항이 명확해졌다’를 문서 예시로 보여 주고, 8장은 ‘테스트 통과’와 ‘올바른 결과’의 차이를 반례로 보여 주며, 12장은 빠른 생성이 실제 성과로 이어졌는지 판단하게 합니다. 세 장을 먼저 써서 책의 논리·실용성·문체를 검증합니다.

### 10.1 조사 과제

| 용어 | 원출처·저자 설명·독자 인터뷰 | 바이브 코딩과 AI 네이티브를 어떻게 구별할 것인가? |

이번 조사에서는 참고 도서의 공개 자료만 확인했습니다. 위 AI 관련 연구·조직 사례는 후속 조사 항목이며, 수집 완료한 근거로 표시하지 않습니다.

### 10.2 주장 기록 필드

각 사실·수치·외부 주장에는 `claim_id`, 해당 장, 주장 문장, 출처 URL 또는 서지·쪽수, 확인일, 연구·관찰 조건, 근거 유형, 한계·반례, 검증 상태, 검토자를 기록합니다. 도구·모델에 종속된 내용에는 버전·실행일을 추가합니다.

근거 유형은 외부 자료, 저자 관찰, 제안 원칙, 가상 시나리오로 구분합니다. 미확인 사실과 제안 원칙을 ‘검증된 모범 사례’로 서술하지 않습니다.

### 10.3 사례 수집 기준

실제 사례는 배경, 팀·시스템 규모, 작업 유형, 변경 전 방식, 개입, 관찰 기간, 결과, 실패·한계, 공개 가능 범위를 기록합니다. 특정 효과를 인과관계로 단정하려면 다른 변화 요인을 검토합니다.

제안 목표는 실제 사례 6건 이상이며, 최소 2건은 기대한 효과가 없거나 실패한 사례로 구성합니다. 신규 개발·기존 시스템·운영 업무를 모두 포함하도록 모집합니다. 사례가 부족하면 가상 사례로 채워 실증한 것처럼 보이지 않게 하고, 수집 기간 또는 주장 범위를 조정합니다.

## 12. 집필 프로젝트 운영

### 12.1 역할

- 저자: 논지, 경험 서술, 최종 사실 확인, 원고 수용을 책임집니다.
- AI 집필 보조: 자료 탐색, 구조 제안, 초안, 교차참조·용어 검사를 수행합니다. 출처 검증과 최종 승인 완료를 스스로 가정하지 않습니다.
- 기술 검토자: 독자적으로 검증 방식과 기술적 주장을 검토합니다.
- 대상 독자 검토자: 이해·적용 과제를 수행해 실용성을 평가합니다.
- 편집 검토자: 중복, 흐름, 문체, 독자 약속과 원고의 일치를 확인합니다.

검토자는 아직 섭외되지 않았습니다. 초기에는 저자가 여러 역할을 맡을 수 있지만 외부 검토 단계의 별도 시각은 확보해야 합니다.

### 12.2 원고 흐름

장별 질문 정의 → 근거·사례 수집 → 개요 → 초안 → 저자 검토 → 기술·출처 검토 → 독자 적용 검토 → 수정 → 원고 수용 순으로 진행합니다.

한 장을 하나의 작업 단위로 관리합니다. 핵심 논지·새로운 사실·큰 구조 변경은 검토 대상으로 남기고, 문장 정리와 오탈자 수정은 간단하게 처리합니다. 실제 집필량·검토 시간을 샘플 장에서 측정해 계획을 조정합니다.

현재 문서는 기업 사이트 저장소의 초안 위치에 저장하며, 책 저장소를 만들 때 루트 `PRD.md`로 옮길 수 있습니다. 인터뷰 원본·비공개 자료는 공개용 저장소와 분리 보관하고 원고에는 허용된 내용만 반영합니다.

## 13. 일정과 단계별 수용 조건

기획 착수 후 12주를 가정한 초안입니다. 저자의 가용 시간과 검토자 일정은 미확정이며, 4주 차 샘플 검토 후 잔여 일정을 다시 산정합니다.

| 단계 | 기간 제안 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
| M1 기획·조사 | 1~2주 | 목차, 용어, 근거 목록, 사례 모집 계획 | 독자·핵심 논지·장별 질문이 일치합니다. |
| M2 샘플 검증 | 3~4주 | 3·8·12장, 대응 템플릿 | 초기 독자 3명이 각 장의 행동을 설명하고 양식을 작성합니다. |
| M3 전체 초안 | 5~8주 | 전체 장과 사례·템플릿 초안 | 모든 장에 필수 요소가 있고 근거 공백이 표시됩니다. |
| M4 외부 검토 | 9~10주 | 기술 검토와 대상 독자 5명 이상 피드백 | 핵심 오해·사실 오류·적용 장애가 기록됩니다. |
| M5 수정·정리 | 11~12주 | 통합 원고, 참고문헌, 최종 체크리스트 | P0 요구사항과 최종 품질 기준을 충족합니다. |

샘플 장 검토에서 실용성이 확인되지 않으면 전체 원고 확장을 멈추고 논지·사례·템플릿을 고칩니다. 사례 확보가 지연되면 일정부터 조정하며 미확인 사례를 완성된 사실로 넣지 않습니다.

## 14. 성공 지표와 최종 완료 기준

### 14.1 책 프로젝트의 성공 지표

아래 수치는 초판 검증을 위한 제안 목표이며 통계적 효과를 입증하는 기준은 아닙니다.

| 항목 | 목표 | 확인 방법 |
|---|---|---|
| 이해 | 검토자 5명 중 4명 이상이 자기 말로 핵심 논지를 설명합니다. | 장을 읽은 뒤 요약과 오해 지점을 수집합니다. |
| 적용 | 5명 중 4명 이상이 자기 업무에 T03·T05·T06을 작성합니다. | 작성 결과에서 누락과 해석 차이를 확인합니다. |
| 근거 추적 | 확인 가능한 외부 사실·수치·인용의 출처 연결률 100% | 주장 기록과 본문을 대조합니다. |
| 사례 품질 | 실제 사례 6건 이상, 실패·제한 사례 2건 이상 | 관찰 근거와 사용 허용 범위를 확인합니다. |
| 내용 완결 | 18개 장과 8종 템플릿의 필수 요소 충족 | 장별 검토표를 확인합니다. |
| 오류 처리 | 공개를 막는 사실 오류·잘못된 인용·노출 문제가 0건 | 검토 기록의 미해결 항목을 점검합니다. |

### 14.2 책이 독자에게 제안할 조직 지표

책의 성공 지표와 조직 운영 지표를 구분합니다. 독자의 조직에서는 고객 수용 결과, 작업 대기와 완료 시간, 재작업·운영 결함, 복구 시간, 사람의 검토 시간, 도구·모델·인프라 비용을 함께 살펴보도록 제안합니다.

코드량·생성 횟수·토큰 사용량·AI 사용률은 단독 성과 지표로 사용하지 않습니다. 지표마다 목적·분모·관찰 기간·수집 조건을 정의하고 작업 난이도와 위험도가 다른 팀을 단순 순위화하지 않습니다. 이 지표 설계의 효과 역시 사례로 확인합니다.

### 14.3 최종 완료 정의

필수 산출물 작성, 근거 확인, 기술·독자 검토 반영, 용어 통일, 링크·교차참조 확인, 미해결 항목 검토를 마친 상태를 집필 완료로 봅니다. PDF·EPUB를 만들 경우 별도로 한국어 글꼴·표 잘림·목차 이동을 시각 검수합니다. 출판 계약이나 판매량은 원고 완성의 전제 조건으로 두지 않습니다.

## 16. 후속 결정과 착수 순서

후속 결정은 저장소 소유자·공개 여부, 저자 가용 시간, 사례 사용 범위, 출판 방식, 최종 분량입니다. 현재 PRD 초안 작성에는 이 결정들이 필요하지 않으며, 관련 실행을 시작할 때 확정합니다.

착수 순서는 다음과 같습니다.

1. 저자가 PRD의 독자·논지·제안 목차를 검토합니다.
2. 저장소와 원고 관리 방식을 정하고 기획을 옮깁니다.
3. 참고 도서 정독과 주장 기록을 시작합니다.
4. 실제 경험 중 공개 가능한 사례 후보를 선정합니다.
5. 샘플 3개 장과 대응 템플릿을 작성해 독자 검토를 진행합니다.
